# 智育助教 —— 改进方案建议

> 面向：项目组（2 人）
> 目的：把「课程 Demo」推进到「一个班能真用」的系统
> 日期：2026-10-29

---

## 0. 一句话结论

| 你关心的问题 | 建议做法（先做→后做） |
|---|---|
| 知识库只有几篇测试文章 | **先建"知识点表"，再按知识点写资料**；资料用「自写 + 开放许可」来源，别整本搬教材 |
| 功能太少 | 先做**学习通式最小闭环**：班级 → 任务 → 提交 → AI 诊断 → 教师看板；在线判题（头歌那种）放最后 |
| 一直烧我的 API key | **Key 永远只在服务端**，加"用量表 + 每日配额"，上线前套一层 **LLM 网关**（LiteLLM / New-API）做 key 池与审计 |

推荐节奏：**第 1 周修坑 → 第 2-4 周做班级/任务 MVP → 第 5-6 周结构化知识库 → 第 7-8 周网关 + 部署**。

## 1. 先分清：你们现在有 3 个"数据库"

很多讨论会绕晕，是因为"数据库"在项目里指了三样不同的东西：

| # | 是什么 | 现在的位置 | 现状 | 该不该动 |
|---|---|---|---|---|
| 1 | **业务库**（用户/会话/消息/剖析记录） | `backend/data/app.db`、`chat.db` | 两个 SQLite，表结构还行 | 合并成一个，加迁移 |
| 2 | **向量库**（检索用） | `backend/data/vector_db/`（ChromaDB） | 89 个分块，能跑 | 保留，元数据要加 |
| 3 | **知识源**（人写的 Markdown） | `backend/data/knowledge/{lecture,solutions,buglib}` | 18 篇，内容薄 | **重点补这个** |

你感觉"数据库是随便找的几篇文章"——问题其实出在 **3**，不是 1 和 2。向量库只是 3 的索引，源内容不行，检索再准也没用。

所以下面把「知识内容」和「业务数据」分开讲。

## 2. 知识库：从"几篇文章"到"一门课"

### 2.1 三个方案

#### 方案 A：Markdown 仓库 + 规范化的元数据（轻量，1 周）
- 目录按 `课程/章节/知识点` 组织，每个知识点一个 `.md`，文件头写 YAML：

```markdown
---
id: ds-03-02
chapter: 03
title: 二叉树的前中后序遍历
difficulty: 2
type: lecture          # lecture | solution | bug | exercise
tags: [树, 递归, 遍历]
prereq: [ds-03-01]
source: 自编
---
## 概念
...
## 常见错误
...
```

- 写个 `scripts/check_kb.py` 校验：id 重复、缺字段、空章节、覆盖度矩阵。
- **优点**：Git 可 diff、可 review、零迁移成本，正好适合你们两人协作。
- **缺点**：知识点之间只有 `prereq` 弱关系，统计"学生掌握了哪个知识点"仍然难。

#### 方案 B：关系库建"知识点表"，向量库只做文本召回（推荐）
- SQLite/Postgres 里加结构化表（见 2.3），向量库存 chunk 时带上 `kp_id`。
- 检索流程变成：向量召回 → 按 `kp_id` 回表 → 拿到难度、前置知识、常见错误、关联题。
- 好处：
  - 能做**掌握度**（`kp_mastery`），教师端才有"学习情况"可看；
  - 能按知识点自动组卷/布置任务；
  - AI 回复可以引用"知识点编号"，学生能跳转。
- 代价：要先花时间标注（80 个知识点 × 10 分钟 ≈ 13 小时）。

#### 方案 C：直接搬现成教材/题库（不推荐）
- 严蔚敏教材、王道考研、各种题库 PDF —— **版权问题**，传到 GitHub 有下架风险，课程答辩也可能被问。
- 可以合法用的：
  - **OI Wiki**（CC BY-SA 4.0，算法竞赛向，质量高）
  - **Hello 算法**（CC BY-NC-SA，图文并茂，适合入门）
  - **MIT 6.006 / 6.046 公开课**（OCW，CC BY-NC-SA）
  - VisuAlgo（演示动画，引用链接即可）
- 建议：**自己写主干 + 引用开放资源 + 教材只做"章节对应关系"不复制正文**。

### 2.2 推荐落地方式

**方案 A 打底，方案 B 增量**——第 5-6 周先把 A 的目录和元数据规范建起来，同时建 `knowledge_points` 表，边写边标注。

具体步骤（2 人分工）：

| 步骤 | 产出 | 人天 |
|---|---|---|
| 1. 定范围 | 只做你们课上的 8 章（链表/栈队列/树/AVL/排序/查找/图/线性表），每章 8-12 个知识点 | 0.5 |
| 2. 建 kp 表 | 约 80 条知识点，含难度、前置、学习目标 | 1 |
| 3. 补内容 | 每个知识点 4 类：讲义（500-800 字）、典型错误（3 条）、练习题（2 道，含分级提示）、代码模板（伪代码级） | 4-6 |
| 4. 升级 ingest | 读 front matter、按 `kp_id` 分块、chunk 400 字 + 50 重叠、写 metadata | 1 |
| 5. 覆盖度检查 | 页面/脚本：章节 × 资料类型 矩阵，空的标红 | 0.5 |

> 内容量参考：80 kp × (1 讲义 + 3 错误 + 2 题) ≈ 480 条，够 RAG 用了；现在是 89 个分块，其中大量是"概述"这种低信息量块。

### 2.3 建议的知识点相关表

```sql
CREATE TABLE courses (
  id INTEGER PRIMARY KEY, name TEXT, term TEXT
);

CREATE TABLE knowledge_points (
  id INTEGER PRIMARY KEY,
  course_id INTEGER,
  chapter INTEGER,
  code TEXT UNIQUE,          -- ds-03-02
  title TEXT,
  difficulty INTEGER,        -- 1-5
  objectives TEXT,           -- 学完能做什么，用于生成任务
  prereq TEXT                -- JSON 数组
);

CREATE TABLE problems (
  id INTEGER PRIMARY KEY,
  kp_id INTEGER,
  title TEXT,
  statement TEXT,            -- 题面
  difficulty INTEGER,
  hints TEXT,                -- JSON：一阶/二阶/三阶提示，配合三阶提示法
  test_cases TEXT            -- JSON，后期在线判题用
);
```

## 3. 功能：教师端 + 学生端

### 3.1 头歌 vs 学习通，分别学什么

| 平台 | 强项 | 对应到你们 |
|---|---|---|
| 学习通 | 班级、签到、作业、资料、成绩、讨论 | **管理骨架**，先做这个 |
| 头歌 | 在线实训、自动判题、闯关、代码评测 | **最难的部分**，最后做或接第三方 |

不要一上来做评测机（Docker + 沙箱 + 判题），那是头歌团队几年的工程。

### 3.2 分三期

#### 一期 MVP（2-3 周，只有一个目标：一个班能跑完一次作业）

```
教师：建班（6 位邀请码）→ 发布任务 → 看提交情况
学生：输邀请码进班 → 看任务 → 提交代码/答案 → 看 AI 诊断
```

功能点：
1. **角色**：`users.role`（student / teacher / admin）
2. **班级**：`classes`（名称、邀请码、学期）、`class_members`
3. **任务**：`assignments`（标题、说明、截止时间、类型：问答 / 代码、关联 kp）
4. **提交**：`submissions`（内容、语言、状态、AI 诊断结果、分数）
5. **教师看板**：提交率、未交名单、错因分布（柱状图）、单个学生的提交时间线
6. **复用现有能力**：AI 诊断直接复用 `analyze_code_stream`

#### 二期（3-4 周）
- **知识点掌握度**：每次对话/剖析/提交 → 记一条 `kp_events` → 聚合到 `kp_mastery` → 学生雷达图、班级薄弱知识点排行
- **教师批注 / 互评**
- **班级讨论区**：AI 先答、教师补充（复用苏格拉底 Prompt）
- **防抄袭**：代码归一化 + 相似度（先做简单的 token 指纹，够用）
- **通知**：站内信 + 邮件（截止提醒）

#### 三期（可选，1-2 个月）
- **在线判题**：`g++` 编译 + 限制内存/时间 + 用例比对。工程量大，可用 **Judge0**（开源，Docker 部署）接
- 学习预警（连续 2 次未交 / 同一知识点连续错）
- 成绩导出 Excel、课程归档

### 3.3 数据模型（一期）

```sql
ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'student';
ALTER TABLE users ADD COLUMN display_name TEXT;

CREATE TABLE classes (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  code TEXT UNIQUE NOT NULL,      -- 邀请码
  teacher_id INTEGER NOT NULL,
  term TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE class_members (
  class_id INTEGER NOT NULL,
  user_id INTEGER NOT NULL,
  joined_at TEXT NOT NULL,
  PRIMARY KEY (class_id, user_id)
);

CREATE TABLE assignments (
  id INTEGER PRIMARY KEY,
  class_id INTEGER NOT NULL,
  title TEXT NOT NULL,
  description TEXT,
  type TEXT NOT NULL,             -- question | code
  kp_ids TEXT,                    -- JSON 数组，统计学习情况的关键
  due_at TEXT,
  created_by INTEGER NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE submissions (
  id INTEGER PRIMARY KEY,
  assignment_id INTEGER NOT NULL,
  user_id INTEGER NOT NULL,
  content TEXT NOT NULL,
  language TEXT,
  status TEXT NOT NULL DEFAULT 'submitted',  -- submitted | analyzed | graded
  score REAL,
  ai_result TEXT,                 -- 完整 AI 回复（Markdown）
  submitted_at TEXT NOT NULL,
  UNIQUE (assignment_id, user_id) -- 一期只允许一次提交
);

CREATE TABLE submission_diagnoses (
  id INTEGER PRIMARY KEY,
  submission_id INTEGER NOT NULL,
  error_types TEXT,               -- JSON: ["断链","内存泄漏"]
  kp_ids TEXT,
  severity TEXT
);
```

### 3.4 关键设计提醒（这个点决定"看板有没有用"）

现在 AI 回复是**纯文本流**，没法统计。要让教师端有"学习情况"，必须**结构化**：

- 一次性生成：要求模型在流式回复**末尾**追加一段固定格式的 JSON（用特殊分隔符包起来），后端流结束后切出来存库；
- 或者流式给用户看，结束后再发一次非流式的小请求，只让它输出诊断 JSON（贵一点，但稳）；
- JSON 建议字段：

```json
{
  "error_types": ["空指针解引用", "循环条件错误"],
  "kp_ids": ["ds-01-03"],
  "severity": "medium",
  "hint_level_reached": 2,
  "next_question": "如果 p 已经是 NULL，p->next 会发生什么？"
}
```

有了 `error_types` 才能画"班级错因分布"；有了 `kp_ids` 才能算掌握度；有了 `hint_level_reached` 才能评估"AI 有没有真的在引导而不是直接给答案"——这本身就是你们课题的一个亮点指标。

### 3.5 权限（做教师端后是安全问题，不是体验问题）

- JWT 里带 `role`，但**每次请求都要回库校验**（现在是直接信 token 里的 user_id）
- 教师只能访问自己班的：`classes.teacher_id == user_id`
- 学生只能看自己的 submission
- 管理员（你们）单独一个角色

## 4. API Key：不能一直烧你的

### 4.1 先明确三条红线

1. **Key 不能出现在前端**（打包进 JS 等于公开）
2. **Key 不能进 Git**（`.env` 已经 ignore 了，但这只保护"未来"；建议顺手排查历史提交）
3. **不能让浏览器直连大模型厂商**（跨域 + 泄露 + 无法审计）

你们现在其实已经是"服务端调用"了，比很多课设好。真正的问题是：**没有用量控制，谁登录都能无限用你的额度**。

### 4.2 四个方案

#### 方案 1：服务端代理 + 每日配额（一周内可做，强烈建议现在做）
- Key 保持只在 `.env`
- 加表 `api_usage(user_id, day, prompt_tokens, completion_tokens, model, cost)`
- 每次调用 LLM 前检查当日额度，超了返回友好提示
- 流式调用加 `stream_options={"include_usage": True}`，收尾时记账
- 教师账号额度高，学生低（比如 30 次/天）
- **成本量级**：按一次对话 1500 输入 + 600 输出 token 估，一个班 40 人 × 20 次/天 ≈ 1.2M 输入 + 0.5M 输出 ≈ 每天几元、每月一两百元（按 DeepSeek 官网现价换算，价格会变，务必以官网为准）
- 这一步解决"失控"，但**钱还是你出**

#### 方案 2：LLM 网关（上线前必须做，推荐）
在后端和厂商之间放一层网关：

```
前端 → FastAPI → LiteLLM / New-API 网关 → DeepSeek / 通义 / 豆包 / 智谱
```

网关能给你们：
- **多 key 池**（几个人的 key 轮询，单 key 限流不影响整体）
- **按用户发子 key**（每个学生一个 key，配额独立，出事可单独封）
- **多供应商路由**（DeepSeek 挂了自动切 Qwen）
- **用量审计**（谁在什么时候烧了多少）
- 换模型/换厂商**不用改业务代码**

推荐开源：**LiteLLM**（Python，OpenAI 兼容，配置化）、**New-API / One-API**（Go，带管理后台，适合给同学发额度）。
部署成本：一台 2C4G 云服务器约 60-100 元/月，或直接用学校/实验室服务器。

#### 方案 3：自带 Key（BYOK）
- 学生登录后自己填 DeepSeek key，加密存库（AES-GCM，密钥在环境变量），服务端调用时解密
- 优点：你们零成本；缺点：学生要自己注册充值，国内课堂大概率不愿意；key 存你们库里也有责任
- 建议只作为**"校外用户/教师"的可选项**，不作为默认

#### 方案 4：降本组合拳
- **换便宜模型**：Qwen-turbo、GLM-4-Flash、豆包 lite，很多有免费额度
- **意图分流**：简单问题（"什么是栈"）走小模型或直接命中知识库；只有诊断类才用大模型
- **缓存**：相同问题（归一化后）命中缓存直接返回，班级里重复提问很多
- **本地模型**：Ollama + Qwen2.5-7B，需要 GPU；实验室有卡才划算
- **申请额度**：阿里云百炼、火山引擎、智谱都有新用户免费 token 包；学校可能有统一采购/教育优惠

### 4.3 建议路线

| 阶段 | 做法 |
|---|---|
| 现在（1 周） | 方案 1：配额 + 用量表 + 服务端记账，先把"失控"止住 |
| 上线前（第 7-8 周） | 方案 2：接 LiteLLM/New-API，key 池 + 子 key + 审计 |
| 应急/外部用户 | 方案 3：BYOK 作为可选入口 |
| 长期 | 方案 4：缓存 + 分流 + 免费额度，把单次成本压下来 |

### 4.4 代码改造点（很小）

```python

    "deepseek": {"base_url": DEEPSEEK_BASE_URL, "model": "deepseek-chat"},

# 新增 app/api/usage.py：GET /api/usage/me（今日用量）、GET /api/usage/admin（全部）
```

## 5. 顺手要修的坑（我实际跑了一遍发现的）

按严重程度排：

| # | 问题 | 后果 | 处理 |
|---|---|---|---|
| 1 | `core/auth.py` 里 `SECRET_KEY` 硬编码 | 任何人可伪造 token，做教师端后等于可以冒充老师 | 改成读环境变量，且**上线前必须换掉** |
| 2 | 前端 `dist/` 提交进 Git，但里面 JS 缺失 | 生产模式打开是白屏（`index.html` 引用了不存在的 js） | `dist/` 加进 `.gitignore`，部署时构建 |
| 3 | `frontend/node_modules` 被提交进 Git | 仓库巨大，clone 慢，冲突多 | `git rm -r --cached frontend/node_modules` |
| 4 | `__pycache__/*.pyc` 被跟踪（18 个） | 每次运行都产生 diff 噪音 | `git rm -r --cached` 后靠现有 `.gitignore` |
| 5 | `backend/data/chat.db` 被跟踪 | 每个人本地数据不同，天天冲突 | 从版本库移除 |
| 6 | 两个 SQLite（app.db / chat.db） | 备份/事务/关联查询都别扭 | 合并成一个，加 `alembic` 或手写 migrate |
| 7 | `rag.py` 里 chromadb 0.4.24 与 numpy 2.x 不兼容 | 新电脑 `import chromadb` 直接崩 | 钉 `numpy<2` 或升级 `chromadb>=1.0` |
| 8 | `sentence-transformers`/torch 在部分 Windows 机器被**应用控制策略**拦截（我这就复现了） | 后端启动即失败 | 换 **fastembed / onnxruntime**（不依赖 torch，体积从 2GB 降到几十 MB，还能上 ARM 服务器） |
| 9 | `/api/knowledge/ingest` 无鉴权 | 任何人都能触发重建（耗 CPU/重下模型） | 加教师/管理员权限 |
| 10 | CORS `allow_origins=["*"]` + `allow_credentials=True` | 生产环境等于放开 | 收紧到具体域名 |

> 第 8 条顺带解决了"部署到服务器"的问题：torch 2GB 在 1C2G 的云服务器上根本装不动，ONNX 版本能塞进小机器。

## 6. 里程碑与分工建议

| 周 | 目标 | 验收标准 |
|---|---|---|
| 1 | 修坑 + 合并数据库 + 配额 | 新电脑 clone 后能一条命令跑起来；超配额有提示 |
| 2-3 | 班级 + 任务 + 提交 | 老师建班发任务，学生进班交代码，能看到 AI 诊断 |
| 4 | 教师看板 | 提交率、错因分布、未交名单 |
| 5-6 | 知识点表 + 内容填充 | 80 个 kp，覆盖度 >80%，检索命中带 kp 信息 |
| 7 | 掌握度 + 雷达图 | 学生能看到自己薄弱知识点 |
| 8 | 网关 + 部署 | 服务器上跑起来，key 在网关上，有用量报表 |

两人分工建议：
- **A（后端/数据）**：数据库重构、班级/任务/提交 API、配额、网关、部署
- **B（前端/内容）**：教师端/学生端页面、看板图表、知识点内容生产、Prompt 调优

每周一次 PR 合并，`main` 分支保持可运行。

## 7. 别做的事（课程项目常见坑）

1. 别一上来做在线判题 —— 沙箱逃逸、编译超时、资源限制，坑比功能多
2. 别同时上微服务/K8s/Redis —— 一个班几十人，SQLite + 单进程完全够
3. 别把教材扫描件传 GitHub
4. 别在前端藏 key（混淆也没用）
5. 别为了"功能多"牺牲"不泄题"这个课题核心 —— 加功能时反复用你们的验收用例回归
