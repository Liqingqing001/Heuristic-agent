## 概念

哈希表（散列表）的思路是**不做比较**：用哈希函数 `h(key)` 把关键字直接算成一个桶下标，理想情况下一次就能定位，平均时间 O(1)——这正是它比二分查找、二叉排序树都更「快」的地方，因为后两者的 O(log n) 本质上是比较次数的下界，而哈希用算术换掉了比较。

但关键字空间通常远大于表长，两个不同的 key 算到同一个下标是必然的（鸽巢原理），这叫**冲突**。冲突处理才是哈希表真正的设计内容，主流两大类：

**开放定址法**：冲突了就按某个探测序列在表内另找空位（线性探测 `(h+i) mod m`、二次探测 `(h ± i²) mod m`、双散列 `(h + i·h₂) mod m`）。所有元素都放在表里，装填因子 α = n/m 必须小于 1，一般控制在 0.75 以下，超了就扩容 rehash。

**链地址法**：每个桶挂一条链表，冲突就插到链上。删除简单、α 可以大于 1，代价是指针开销和更差的局部性。

衡量一张哈希表好坏的核心指标不是「有没有冲突」，而是**平均查找长度 ASL**（成功、失败分别算），它由哈希函数是否均匀和装填因子共同决定。哈希函数最常用除留余数法 `h(k) = k mod p`，p 取不大于表长的最大质数——因为合数（尤其 2 的幂）会把关键字的低位规律直接放大成聚集。

```text
插入(key):                        // 开放定址：线性探测
    i = h(key); cnt = 0
    while table[i] 非空 and cnt < m:
        i = (i + 1) mod m         // 回绕，不能写成 i++
        cnt++
    if cnt == m: 表已满 → 扩容并 rehash
    table[i] = key
```

## 要点

- 冲突不可避免，哈希表的设计重点是「冲突怎么处理」+「装填因子控制在多少」，不是「怎么做到没有冲突」。
- 开放定址法删除必须打墓碑（DELETED）标记，不能直接把槽位置空，否则探测链断裂。
- ASL成功 = Σ每个关键字的探测次数 ÷ n；ASL失败 = Σ每个哈希地址探测到空槽的次数 ÷ m，两个分母不同，别混用。
- 除留余数法的 p 取不大于表长的最大质数；表长取 2 的幂会把低位规律放大成二次聚集。
- 线性探测在 α → 1 时探测长度急剧恶化；查找成功时平均探测次数约 (1 + 1/(1-α))/2，所以 α 一般压到 0.75 以下。
- 链地址法查找时间与链表长度成正比，平均链长就是 α，所以功能上允许 α > 1，但查询会变慢。

## 典型错误

### 错误 1：开放定址法删除时把槽位直接置空

- 现象：删掉一个元素后，另一个本来查得到的元素突然查不到了；把刚删的元素重新插回去又「恢复」；这个 bug 只在删除后出现，插入和查找的单元测试全绿。
- 原因：查找的失败判据是「探测到空槽就认为不存在」。中间某槽被置空后，探测链在那里断掉，排在它后面的同义词全部失联——它们明明在表里，但查找走到那个空槽就返回了失败。
- 引导问题：查找时你凭什么判断「这个 key 一定不在表里」？这个判断依赖探测路径上每个槽的什么信息？如果中间有个槽被清空了，这条链还连着吗？

### 错误 2：线性探测的下标更新漏了取模，从表尾越界

- 现象：表很空时一切正常，表快满（或 h(key) 落在 m-1 附近）时程序崩溃或写坏邻近变量；用 AddressSanitizer 才看到数组越界。
- 原因：写成 `i = i + 1;`，或只在 `if (i == m) i = 0;` 时清零但循环里已经先访问了 `table[m]`。正确写法是每次 `i = (i + 1) % m`，让 `m-1` 的下一个回到 0。
- 引导问题：探测到最后一个桶 `m-1` 还冲突时，下一个该看哪个桶？这个下标怎么用一次运算就得到？

### 错误 3：查找循环没有探测次数上限，key 不存在时死循环

- 现象：查一个不存在的 key 时程序卡住不返回；表里有很多墓碑或几乎装满时更容易复现。
- 原因：写成 `while (table[i] != key) i = (i + 1) % m;`，既没判空槽也没有 `cnt < m` 的上限。表里没有这个 key 又找不到空槽时，指针绕着表永远转圈。
- 引导问题：如果整个表里都没有这个 key，这个循环靠什么条件才能停下来？这个下界条件你现在写了吗？表满的时候又该怎么收场？

### 错误 4：算 ASL 失败时分母用了 n，或探测次数算到表尾

- 现象：ASL失败 与标准答案对不上，m 与 n 差得越多错得越多；有的同学同一张表算出 2.5，答案却是 3.2。
- 原因：失败查找的起点是每一个可能的哈希地址（共 m 个），分母必须是 m 而不是元素个数 n；而且探测次数算到「第一次遇到空槽」为止，不是算到表尾或算完整张表。
- 引导问题：一次失败的查找是从哪里开始的？一共有多少个可能的起点？你数到哪一格就停下来了？

### 错误 5：哈希函数用 k mod 2^k 或表长取合数，冲突集中成一段

- 现象：数据能存进去也能查出来，但 ASL 明显偏大，探测序列出现一长串连续被占用的槽；换个表长就好了。
- 原因：除留余数法取 `p = 表长` 且表长是 2 的幂或 10 的倍数时，`k mod p` 只保留关键字的低位，关键字的规律位直接变成聚集；p 取质数能让余数分布更均匀。
- 引导问题：表长取 2 的幂时，`k mod 16` 用到了 k 的哪几位？如果关键字的低位全是偶数，会集中落到哪些桶上？

## 分级练习

### 练习 1：手工建表并算 ASL（难度：2）

- 题面：关键字 `{12, 25, 38, 15, 51, 29}`，表长 m = 7，`h(k) = k mod 7`，用线性探测处理冲突：画出最终的表，再算 ASL成功 和 ASL失败。
- 一阶提示（反问）：29 算出来的地址是 1，可是 1 号桶已经被 15 占了——接下来按什么顺序找下一个空位、找到后要记成探测几次？
- 二阶提示（定位到行）：探测次数从 1 开始计（第一次落在 h(k) 上就算一次）；算 ASL失败 时，起点是 7 个哈希地址 0..6，每个起点一直数到「遇到空槽」为止，空槽本身也算一次。
- 三阶提示（伪代码/类比）：像停车场找位子：你的指定车位被别人占了，就往后一辆一辆找空位，找了几辆就记几次；失败查找则是「从某个门牌号开始往里走，直到遇到一间空屋子才知道这排没有」。
- 验收点：表里 0 号桶为空，1..6 依次为 15、51、38、25、12、29；29 的探测次数是 5；ASL成功 的分子是各关键字探测次数之和、分母是 6；ASL失败 的分母是 7 且每个起点数到第一个空槽为止。

### 练习 2：补全开放定址的查找并统计探测次数（难度：3）

- 题面：写 `search(key)` 返回「是否找到 + 探测次数」；要求 key 不存在时能在有限步内判定失败，遇到墓碑（DELETED）要继续探测、只有真正的空槽才停。
- 一阶提示（反问）：什么样的槽位才允许你「确定放弃」？墓碑算不算这种槽位？如果一路全是墓碑，你靠什么跳出循环？
- 二阶提示（定位到行）：循环里要同时维护 `cnt` 与表长 m 的比较；三个分支的判断顺序是「空槽 → 失败」「命中 → 成功」「墓碑 → 继续往前」，不能把它们合并成一个 `if`。
- 三阶提示（伪代码/类比）：像沿走廊挨个敲门：门上有名字且对得上就找到了；一间彻底空着的房间说明后面没人住了，可以回头；贴着「已搬走」的房门还得继续往前问。
- 验收点：找到时探测次数与手工算的一致；不存在的 key 最多探测 m 次就返回失败；删过元素后仍能查到后面的同义词；墓碑不会被误判为命中。

### 练习 3：设计链地址法并处理扩容 rehash（难度：4）

- 题面：用链地址法实现哈希表，说明装填因子超过 0.75 时怎么 rehash，并解释为什么链地址法的删除不需要墓碑、而开放定址法必须打。
- 一阶提示（反问）：扩容以后原来的下标为什么不能照抄？`h(k)` 用的是新的表长，说明每个 key 的哪一个量变了？
- 二阶提示：新表长取原表长约 2 倍附近的质数，遍历所有旧结点、按新表长重算下标再插入；链表删除只需让前驱的 next 跨过目标结点（首结点则改桶头指针），被删结点可直接释放。
- 三阶提示（伪代码/类比）：像把一排信箱拆掉重装成两排：每封信的门牌号都得按新编号重新算一遍，不能整箱搬过去；而链表法里拿走一张卡片不会让后面的人找不到路，开放定址里挖掉一格却会把整条队断成两截。
- 验收点：扩容前后所有 key 都能查到；删除后链表不断、不留悬空指针；装填因子始终控制在 0.75 附近；同一批数据下 ASL 比扩容前明显下降。
